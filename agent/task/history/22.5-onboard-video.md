# 任务1 机载摄像头相关服务

实际在生产环境中，摄像头是安装在飞机上的，也就是说需要飞机上的摄像头连接机载计算机，进行推流录像抓拍动作。因此我们现在要实现一个机载摄像头模块，要求如下

1. 它的核心实现方法应该与地面站的尽量完全相同（技术栈什么的，例如地面站是Ffmpeg+mediaMTX, 则飞机上尽量也是FFmpeg+mediaMTX，如无必要，不引入新的依赖，不增加软件栈的复杂度）

2. 它应该是一个相对独立的功能模块，能够独立于机载控制服务开启和关闭。若飞行时摄像头卡死，损坏，或推流失败 或其相关服务出现故障，不能阻塞或影响到机载的飞控服务。摄像头故障、未安装或服务关闭都不会影响飞行控制状态链。

   将相关代码存放在video_service目录下（src/onboard_control/video_service, 或者src/video_service , 这两种，我不清楚哪个更合理。你从中选择一个更合理的方案即可）

3. 它应该与地面站或onboard_control通过ros消息进行通讯，消息传播大概是：

   1. 与飞行相关：我方地面站 <->onboard_control <-> video_service
   2. 与飞行无关（地面站摄像头面板里的相关东西，纯视频业务）：我方地面站 <-> video_service

4. ”摄像头的开启与关闭“和“摄像头服务功能的开启与关闭”相绑定。在摄像头设备开启时，自动启动推流，录像，监听抓拍等所有摄像头服务功能；关闭时则终止所有功能并关闭摄像头

5. 摄像头模块有两个开关入口：

   1. 无论以任何方式起飞（地面站指令，遥控器等），只要飞机起飞，onboardcontrol就在起飞时向videoservice发消息并开启，在降落后发消息并关闭。
   2. onboardcontrol接收来自地面站的直接的开启/关闭命令后，执行开启/关闭

6. 抓拍指令有两种来源：

   1. 地面站将巡检任务（执行航点）发给onboardcontrol后，onboardcontrol解析任务信息，并在飞机每到达一个巡检点位（每完成1个航点执行任务）时，向videoservice发一个抓拍指令
   2. 地面站通过摄像头面板直接发送抓拍指令

7. 抓拍得到的图片的命名规范

   + 所有抓拍到的图片的命名中都应该有当前时间，以便于在任何情况下都能判断出抓拍的先后顺序

   + 若巡检任务或某个航点来自甲方上位机，则onboardcontrol应当把甲方发来的“photoNo”传递给videoservice. 抓拍得到的图片命名中应当体现甲方命令里的“photoNo”编号

     （之前我们没实现这个功能，所以甲方的photoNo直接丢弃了，现在要利用起来）

     此处不对甲方编号进行合法性判断，原样保留。例如，它的编号不严格递增等，不进行修正

   + 若某个航点是我方地面站手动添加，即此航点信息不包含photoNo等，则命名中要体现是地面站控制拍摄的（命名中包含gcs）（以此种方式抓拍第一张就是gcs-1, 第二张就是gcs-2, ...）；

   + 若某次抓拍是直接从地面站摄像头面板发送拍照指令拍摄的，而不是到达航点自动拍摄的，则命名中要体现是手动抓拍（命名中包含manual）（...-manual-1,manual-2,...）

8. 视频和图片保存地址，按照甲方通讯协议即可

   即 视频在 home/share/

   图片在home/share/jpg/

   注意，只要是执行航点任务，不论是来自甲方地面站还是我们手动设置的航点，都要保存图片和视频，都是到这个目录下。

   所有图片格式是jpg

   录制的视频文件的命名包含时间即可，不区分任务类型

   相应地，要实现之前暂时没实现的给甲方发的信息（”videoPath, JPGPath, pointPic等字段）、

   

   甲方的“cameraAngle”字段，继续忽略，本次依然不处理

9. 在机载服务的文件里面，单独提供一个配置摄像服务参数的配置文件，包括：

   + RTSP推流端口， 路径等稳定参数
   + 分辨率（长宽），帧率
   + 编码方式 （H264 或 MJPEG）
   + 图片保存地址（默认为甲方提供的那个）
   + 视频保存地址（默认为甲方提供的那个）
   + 图片保存格式（默认为jpg）
   + 视频保存格式（默认为mp4）
   + 需要注释说明每个参数的用处，以及这个摄像头设置之后能生效的参数范围或组合。如果不适合用注释说明就单独写一个文档，以供用户参考，从而避免用户设置里不合法的参数组合。（但不强制校验，用户填什么就用什么）
   + 重启摄像头后生效

10. 在机载服务的文件里面，再单独提供一个镜头参数的conf配置文件，专门配置镜头参数（曝光值，亮度什么的）

    + 需要注释说明每个参数的用处和摄像头被修改前的默认参数值，以及合法的最大最小范围。如果不适合用注释就单独写一个文档以指导用户（但不强制校验。用户写什么就用什么）

    + ```
      auto_exposure=1
      exposure_time_absolute=25
      gain=200
      ```

      这三个参数为我指定的这三个值；

      ```
      brightness=6
      contrast=6
      saturation=6
      hue=0
      sharpness=6
      power_line_frequency=1
      zoom_absolute=10
      ```

      这几个则用默认值

      暂时不用其他镜头参数

    重启摄像头后生效

11. 推流的IP（也就是自己局域网内的ip），端口号，路径，由video_service通过ros发布，从而让地面站可以自动检测到

# 任务2 地面站逻辑适配与修改

将地面站的摄像头服务的UI与逻辑进行修改适配：



## 核心要求

我希望能够兼容三个模式：

1. 本地计算机接了一个摄像头，能本地检测摄像头设备，就跟当前界面所实现的功能差不多；能调编码方式 分辨率什么的
2. （在地面站成功连接实机的情况下）地面站所连接的真机上接了一个摄像头，能自动检测真机上的摄像头设备（的推流ip 端口 地址）；不允许修改任何参数
3. 不需要本地或飞机上的摄像头，不需要任何摄像头，直接通过RTSP从指定地址拉流，也不允许修改任何参数



都在“摄像头配置面板”里面修改或完成。不能破坏当前摄像头配置面板与地面站本体的独立性



## 其他修改





1. 把RTSP实时画面的逻辑改成：从所填入的地址以RTSP协议进行拉流；即使是本机接了一个摄像头，这个摄像头面板里的画面也应该是自己拉流得到的。（如果已经是这样实现的则不用管）
