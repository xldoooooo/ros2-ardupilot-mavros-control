# websocket 通讯集成实现



## 具体要求



先做一次全量可回退备份，然后再进行修改。在遵守我的要求与AGENTS.md, 做最小化实现 的前提下，按照你最推荐的方法，实现与企业方上位机的wekbsocket通讯功能集成。以下为我的具体要求与注意事项：



1. 本次任务中不连接或使用真机，由仿真验证。当然，我希望连接真机后也能正常工作。

2. 不得出现“甲方””企业方“字样，涉及称呼对方的，一律用”上位机”替代。例如，日志中显示的消息不能是“收到甲方地面站xxxx：，xx”，而只能是“收到上位机xxxx”

3. 我希望的是，本地面站处理对方地面站发来的信号，处理成无人机能理解的遵守本地面站与我方无人机之间通讯协议的消息格式，然后发给无人机。由于对方地面站里对飞机的操作模式与我们自己内部的逻辑并不一直，或者并不能一一对应，例如，对方地面站有一个：“紧急停机”，实际上应该对应的是一个动作组合（停止当前所有任务，悬停，降落；或者直接降落），并不存在一个现成的“紧急停机”命令能直接使用。

   我希望这个映射关系能单独在一个文件里，后续调试或修改都比较方便

4. 尽量抽离到integration或其他单独文件夹中，形成一个类似插件的子模块，专门处理与甲方地面站的通讯，并向地面站本体输出经过处理后的无人机动作指令。默认随着地面站启动而启动，但可以单独与甲方地面站连接/断开/重启，减少与地面站主体的耦合。地面站本体则将命令发送到无人机。

5. 尽量不改动原地面站，且原地面站在不连接对方地面站的情况下依然100%可正常工作。

6. 在地面站主GUI上添加一个按钮“上位机通讯面板”按钮，点击后打开相应的面板窗口或新标签页，展示ws的url，指令映射，消息日志，无人机编号，各通讯json格式等各个相关配置

   在这个通讯面板里面，展示双方websocket接收和发送的json格式原始报文日志。地面站的GUI里的日志模块应只显示供人类维护者阅读的日志，而不要展示这些报文。

7. 机载服务也是同样的道理，尽量不改动现有机载服务；尽量独立/解耦；能通过现有代码实现/组合或计算实现的功能则不要另外新增； 相机、云台、照片和媒体暂时不实现。关闭或崩溃时，原地面站行为完全不变

8. **当地面站运行在仿真模式时，所有对方发来的指令都应作用在仿真当中；**当地面站已经连接实机时，所有对方发来的指令才会作用在实机上。若地面站既没有仿真，也没有建立实机连接，则报告并拒绝执行所有操作。

9. 地面站成功接收并给无人机发送指令后，地面站GUI界面应当有与人手动操作地面站相同的反馈，状态需要同步/一致。例如，添加航点后，地面站GUI右侧航点列表应该会显示出来，就跟我手动在地面站GUI添加相同的效果；等等。不能出现：对方地面站已经将飞机起飞了，而我方地面站的GUI上起飞按钮还是绿色， 类似于这种的不同步现象。

## 具体行为规定



1. 若对方发送：执行巡检任务，而我方无人机并未起飞，则拒绝执行

   若有其他不符合执行条件的命令，也都拒绝执行（例如未起飞的状态下点一键返航）

2. 对方通讯协议里有一些意义模糊或暂无意义的字段，其处理方法如下：

   1. forwardAngle：按照偏航角处理，单位为 角度
   2. cameraAngle：忽略
   3. "photoNo": 忽略

   以上忽略的字段，随着项目进展到后期会用上，因此现在先只输出一个日志，预留一个后续真正处理的接口即可

3. 对方通讯协议里的“**无人机****上报自身状态**”  这一节的内容，

   > 1. ​	通过消息队列去实现主动上报状态，自动写消息到队列中；
   > 2. ​	位置信息、电量信息每1秒上报一次，无人机上电后数据有效；
   > 3. ​	其余状态信息发生时上报。
   > 4. ​	**状态信息根据业务需要必需设置消息过期时间，以免造成消息堆积。**

   具体处理方法如下：

   1. 针对第一条，不需要按照他的要求。我们以合理的方式实现即可，如果它描述的问题本不存在，则直接无视这一条要求
   2. 针对第二条，按其描述实现。电量当前只需传回电压（实机）或百分比（仿真）即可
   3. 针对第三条，按其描述实现。当飞控状态，控制权，航点执行进度等发生变化时，发送消息
   4. 针对第四条，不需要按照他的要求。我们以合理的方式实现即可，如果它描述的问题本不存在，则直接无视这一条要求

   1. 01编号：当前阶段，先不实现。（即任何情况下都不发送这个01）。这个功能后续会实现，现在还没有对异常状态的判定逻辑
   2. 02编号：按描述实现即可。这里只需我方地面站成功添加航点，就向对方报告，也就是说这条消息是从我方地面站发到对方地面站，不经过我方无人机
   3. 03编号：按描述实现即可。在无人机刚开始执行航点任务时发送一条即可，在巡检过程中不再重复发送
   4. 05编号：按描述实现即可。在无人机刚开始返航时发送一条即可，过程中不重复发送
   5. 07编号：按描述实现即可。在无人机刚开始降落时发送一条即可，过程中不反复发送
   6. 08编号：按描述实现即可。在无人机完成执行最后一个航点时发送。预期效果应该是GUI右下的航点执行进度条满的时候发送（内部判定逻辑要一致）
   7. 09编号：按描述实现即可。在无人机到达一个航点时发送。预期效果应该是GUI右下的航点执行进度条每完成一格进度的时候发送（内部判定逻辑要一致）
   8. 0A编号：按描述实现即可。仿真模式时只上报电池百分比即可，实机只上报电压即可
