# correction_service 可配置的解码/发布限频

本报告记录软件限频实现、refresh 负载实测及地面站标定验证；不把采集进程降幅当作整机降幅。

## 实现与配置

活动配置 `correction_service/config/camera.conf` 及 UQ212/Wasintek 档案新增：

```ini
# fps 仍请求相机原生模式；UQ212 保留 120。
fps = 120
# 解码/ROS 发布平均频率上限；0 表示不限制。
publish_fps = 30.0
```

- 缺省值为 30.0；允许有限非负数，0 用于关闭限频；负值/NaN/无穷拒绝。
- `CameraProcess` 向本包 UVC 节点传递独立 ROS 参数 `publish_fps`。
- 使用真实 V4L2 采集单调时间的固定节拍，在 MJPEG 解码前丢弃多余帧。连续读取、归还设备
  缓冲区，不通过 sleep 控频，不改图像时间戳，不复制旧帧；源帧较慢时不补帧，断流后跳过空档。
- 固定节拍避免 59.94 fps→30 fps 时，因每次以当前帧重新设置截止时间而退化到约 20 fps。
  控制的是平均频率，离散源帧和抖动可使相邻输出间隔不完全相等。
- `CAMERA_HEALTH` 增加主动限频丢弃数 `rate_limited`，与 stale/nonmonotonic 分开统计。
- 修改配置后重启独立修正服务生效；无新依赖。未改相机曝光、内外参、图像尺寸/方向、标定
  算法、10 Hz 检测参数、质量门限、extnav 或飞行代码，用户原有工作树改动保留。

## 采集负载对比

refresh 原生 1080p MJPEG 请求保持 120 fps，当前实际源流约 60 fps。测试使用同一份新代码，
仅切换 `publish_fps=0/30/30/0`，每段预热 4 秒、测量 10 秒；本机独立 DDS domain 230 的
Python 消费者接收真实 1920×1080 mono8 图像。不修改生产 correction/extnav 状态。

CPU 通过 `/proc/<pid>/stat` 计算，**100% 表示占满一个 CPU 核**；排除进程启动阶段。

| 指标（两次均值） | 不限频 | 限制 30 fps |
| --- | ---: | ---: |
| 采集进程 CPU | 72.68% | 43.06% |
| 测试订阅进程 CPU | 28.66% | 15.74% |
| 测试订阅端实际接收频率 | 47.75 Hz | 24.15 Hz |
| 订阅回调观察的平均帧龄 | 32.94 ms | 35.25 ms |

采集进程 CPU 下降 **40.8%**，测试订阅进程下降约 **45.1%**。节点自身日志的稳定发布频率
从约 60.10 Hz 降至 29.95～29.97 Hz；限频后稳定采集到解码平均帧龄约 26.07～26.78 ms，
`stale_dropped=0`、`nonmonotonic_dropped=0`，退出码全部为 0。

必须区分发布与交付：本测试消费者使用 best-effort、depth=1，实际接收频率低于发布频率，
不能声称每个订阅者都完整收到 30 fps。其平均回调帧龄增加约 2.31 ms，未出现随时间增长的
积压。测试时运行环境、调度和 CPU 动态频率会影响结果；未分离其各自原因。

本测试证明采集/传输相关开销下降，**未测得完整 correction 算法链或整机总 CPU 的下降比例**。
USB 原始传输仍保留原生流，不因软件限频而减半。
