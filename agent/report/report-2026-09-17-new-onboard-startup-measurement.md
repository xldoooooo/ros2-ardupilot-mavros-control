# new 飞机机载启动耗时实测

本报告记录 drone-new 的实际生产启动链、被动状态采样和一次受控服务重启；未修改生产代码、参数或部署配置。

## 测试边界

- 用户明确指定 drone-new；连接后确认主机 hostname=nvidia、飞控 MicoAir743v2 / ArduCopter 4.6.3、串口 /dev/ttyTHS1:460800。
- 实际自启 unit 是 ros2-ardupilot-onboard.service，ExecStart 调用项目 start_onboard_control.sh。onboard-control.service 不存在，不能以该名称 inactive 判断四组件未运行。
- 重启前只读确认 armed=false、STABILIZE、controller_active=false、lease_active=false，无活动命令；只重启上述 unit，保留飞控上电。未申请控制权，未发送解锁、起飞、模式、运动或原点命令。
- 生产节点启动本身会配置遥测消息频率，Odin/extnav 重启会重建其会话。测试没有应用修正或清除修正的操作。
- new 仓库有大量已有修改与未跟踪文件，未覆盖、同步或构建；不假定与开发机完全一致。
- 状态采样使用 ROS CLI，解析采用开发机项目 .venv；未在飞机上运行额外系统 Python 脚本。

## 实测结果：稳定时钟下重启

以 systemd 启动新服务的单调时间 110.512874 秒为起点，不包含先停止旧服务约 5.19 秒。

| 阶段 | 单调时间（自开机秒） | 相对启动（秒） |
| --- | ---: | ---: |
| 开始执行服务 | 110.513 | 0 |
| MAVROS 被拉起 | 116.939 | 6.426 |
| 飞控心跳连接 | 118.832 | 8.319 |
| 四组件全部拉起、进入 READY 等待 | 119.951 | 9.438 |
| onboard 节点初始化日志 | 120.761 | 10.248 |
| 消息频率配置 ACK | 121.365 | 10.852 |
| 首个 Odin 样本 | 122.418 | 11.905 |
| EKF 使用 external nav | 122.478 | 11.965 |
| MAVROS 参数表完整接收 | 154.523 | 44.010 |
| 推力参数通过校验 | 161.261 | 50.748 |
| 脚本打印 READY | 164.656 | 54.143 |

连续 ControlStatus 采样在 epoch 1789580892.536942362 已显示位置有效、消息频率配置成功，只有 thrust_mode_verified=false；到 epoch 1789580931 左右该项才通过。所有收到的状态都未武装、无控制租约。

只读查询在相对启动约 38.60 秒时，GUID_OPTIONS 返回 Parameter not set，对应 MAVROS 参数类型未取到日志；随后 MOT_THST_HOVER 可读为 0.22387804090976715。没有修改这些飞控参数。

因此实际慢点是：

1. 入口预检与 ROS 环境/包发现约 6.4 秒，串行拉起四组件约 3 秒。
2. 外部定位链约 12 秒已经正常，不是等待 GPS，也不是 EKF 花了 44 秒。
3. 当前 MAVROS 完整参数同步到第 44 秒才结束；尚未单独采集 PARAM_REQUEST_LIST 和各 PARAM_VALUE 的串口时序，不能把这 44 秒全部解释为串口传输。
4. onboard 从自己观察到飞控连接起固定等 40 秒，再读 GUID_OPTIONS/MOT_THST_HOVER，所以到约 50.75 秒才核验；相比参数表完成又晚约 6.74 秒。
5. 脚本循环重新创建 ros2 topic echo，并有轮间 sleep，READY 打印比节点核验又晚约 3.40 秒。

## 明确发现的开机计时缺陷

此次自然开机日志提供了另一个独立证据：

- 单调时间 18.900 秒：脚本开始等待 READY。
- 单调时间 43.990 秒：systemd-timesyncd 首次校时，墙钟从 9 月 16 日 21:08 左右跳到 9 月 17 日 01:46:53。
- 单调时间 45.870 秒：脚本报告完整就绪等待超时，实际只等了约 26.97 秒，远小于设定 120 秒。
- 单调时间 54.583 秒：参数表接收完成；61.472 秒：推力参数通过，但脚本已退出 READY 等待循环，不会补打印 READY。

脚本使用 Bash SECONDS 计算 readiness_deadline，当前平台表现受校时跳变影响。这个超时应改为单调时钟。不能把问题通过等待外网 NTP 或取消就绪门掩盖；离线启动仍须可用。

## 建议与未覆盖项

- 修正 READY 截止时间的单调计时，并显示未通过的具体条件。
- 提前只读检查必要参数，未可用时重试，保留参数值校验；单独调小 40 秒不可能让本次流程 12 秒就绪，因为第 38.6 秒 GUID_OPTIONS 仍不可读。
- 若进一步显著提速，需要核对已安装 MAVROS 的参数同步实现与请求时序，评估优先读取必要两参数，而非让准备状态依赖整表；本次没有实施该改动。
- 持续订阅状态可以减少重复 CLI/DDS 发现造成的额外 READY 延迟；并行拉起需保持现有监督/清理语义。
- 本次一个自然开机样本加一次稳定时钟服务重启；没有人为修改时间，没有飞控重启、解锁或飞行。不能把结果当作实飞验收或所有冷启动耗时分布。

## 结束状态

原 ros2-ardupilot-onboard.service 已恢复 active，脚本成功打印 READY；最终只读快照 armed=false、STABILIZE、lease_active=false、controller_active=false，位置/消息频率/推力校验均有效，100 Hz 控制循环 deadline_miss_count=0。测试订阅有 timeout 自动退出，没有留下新增控制服务。
