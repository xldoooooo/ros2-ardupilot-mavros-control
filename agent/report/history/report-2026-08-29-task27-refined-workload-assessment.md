# Task 27（refined）工作量与难度评估

## 1. 简要结论

如果“完成”仅指复用现有 demo，让摄像头识别一个 AprilTag，并在终端打印一次
`x/y/yaw` 修正量，那么熟悉 OpenCV 和坐标变换的人在环境顺利时用 **1～2 天**做出概念演示是
可能的。

但 `27-tag-odin-fix-refined` 的任务正文要求的不是这个演示，而是一条能够接入现有飞机生产链、
具备时间同步、质量判断、事务式应用、故障隔离、数据不断流、地面 UI、部署、日志、自动测试和
真机验证的完整功能。按一名熟悉 ROS 2、视觉几何和 ArduPilot/MAVROS 的资深工程师估算，在现有
内外参、AprilTag demo 和可用飞机均已准备好的有利前提下，合理工作量约为：

- **25～40 人日，即约 1.2～2 个工作月；**
- 对项目、Odin 或 ArduPilot 不熟悉的工程师，通常需要 **40～60 人日；**
- 多人可以缩短日历时间，但真机、摄像头和部署环境是共享串行资源，不能按人数线性压缩；
- 若还要求完成实飞、30 m 范围 0.1 m 精度证明、飞行振动条件验证以及 MAVLink estimator reset
  的正式实现，则属于下一阶段，通常还需 **1～3 个月**，不包含在当前已完成的台架范围内。

因此，对 refined 任务按“月”而不是按“一两天”估算是合理的。双方判断的差异，本质上来自对
“完成”的定义不同：老师说的一两天更接近算法原型，而 refined 文档定义的是系统工程交付。

## 2. 任务实际包含什么

该任务跨越了多个原本独立的技术域：

1. AprilTag 检测、PnP、相机内外参和完整 SE(3) 坐标链；
2. 从空间变换中提取 SE(2) 修正，正确处理旋转和平移耦合；
3. 图像与 400 Hz Odin odometry 的历史时间匹配；
4. 多帧统计、离群值剔除、收敛/发散和质量门；
5. ROS 2 消息、服务、任务状态机、start/stop/status/result；
6. extnav 中的位置、姿态、速度、协方差修正及 identity passthrough；
7. Odin session、revision、CAS ACK、重启失效和服务退出保留语义；
8. 相机独占、镜头参数、进程组清理、日志和失败恢复；
9. 与飞控生命周期解耦的 systemd、构建和安全部署；
10. 地面站子面板以及 raw/corrected/MAVROS final 三路观测；
11. 自动化测试、性能测试、生产环境备份和真机台架回归。

实际交付涉及 54 个文件、5,916 行新增；其中修正服务和 extnav 的核心 Python 实现约 3,800 行，
另有 ROS 接口、配置、部署脚本、GUI、测试和文档。代码行数本身不能直接换算工期，但足以说明这
不是在现有 demo 上增加几行公式。

## 3. 复杂和困难的主要原因

### 3.1 难点不是“能否识别 Tag”，而是时空对齐

识别结果必须对应图像曝光时刻的飞机位姿，不能使用识别完成后的“最新 Odin”。真机调试发现
相机时间戳使用主机 ROS 时钟，而 Odin header 使用设备运行时钟，两者 epoch 完全不同。直接相减
会得到荒谬结果；简单改用最新值又会把运动、调度和识别延迟变成位置误差。

因此需要保存 odometry 历史、判断时钟是否同源、选择严格 header 或接收时间历史匹配，并对误差
设置硬门。这类问题通常只有接上真实设备才能暴露，也是纯离线 demo 无法覆盖的部分。

### 3.2 坐标修正会直接进入飞控估计链，错误可能“看起来正常”

修正不能分别给 `x/y/yaw` 加常数，而必须左乘 SE(2)。除位置和姿态外，世界系线速度及有效协方差
也必须一致旋转，同时保持 z 不平移。坐标系方向、矩阵乘法顺序或四元数符号错一次，程序仍可能
持续输出数值，却会让航点世界坐标整体旋转或漂移。这类静默错误比编译失败更难发现。

### 3.3 这是带状态的事务，不是一次函数调用

refined 要求只有候选质量合格、extnav 明确 ACK 后才更新 active 修正；失败、超时、相机占用或
correction_service 崩溃都不能改变旧修正或中断 Odin 数据。Odin 重启后旧修正又必须立即失效。

这需要 session、revision、CAS、幂等 ACK、单任务互斥、明确终态和失败恢复。它解决的是并发与
故障状态下“哪组修正才是权威值”，工作性质接近一个小型分布式状态机，而不是视觉公式本身。

### 3.4 原链路必须始终可用，改造空间受严格约束

extnav 是正在使用的生产链路。新模块既要能修正数据，又不能成为新的单点故障；接口包缺失、服务
退出、修正无效时仍需 identity 透传，原始 Odin 话题也必须保留。部署前还要备份生产环境，安装
脚本不能擅自重启正在运行的飞控。

“新增功能能运行”与“新增功能失败时旧系统仍能运行”是两种不同的工程目标，后者通常需要更多
架构设计和故障注入测试。

### 3.5 真机调试具有不可预测性和串行性

本次真实暴露了多项无法从任务文字提前精确推算的问题：

- `v4l2-ctl` 枚举值带文字说明，旧解析方式失败；
- 相机和 Odin 时钟 epoch 不一致；
- 空闲时长期订阅 400 Hz Odin 消耗约 0.866 个 CPU 核，必须改成按需订阅，优化后才降至
  约 0.02 核；
- rclpy 在 SIGINT 后重复 shutdown，使正常停止被 systemd 误判为 failed；
- Tag 摆放并非已知严格世界方向，只能验证链路，不能虚构世界精度结论。

每个问题都需要复现、定位、修改、重新部署和回归。真机、摄像头和 ROS 图谱同一时间只能被有限
数量的实验占用，因此即使增加人手，也不能完全并行。

## 4. 自下而上的人日估算

| 工作项 | 资深工程师估算 |
|---|---:|
| 需求拆解、坐标/故障语义和接口设计 | 2～3 人日 |
| 生产环境调查、配置提取、备份与部署方案 | 2～4 人日 |
| 检测、SE(3)/SE(2)、时间同步和稳健估计 | 5～8 人日 |
| ROS 2 状态机、相机生命周期、日志与配置 | 4～6 人日 |
| extnav 变换、CAS/session 和不断流保底 | 4～7 人日 |
| 地面 UI、构建、systemd、文档 | 3～5 人日 |
| 自动测试、真机调试、性能优化与回归 | 5～10 人日 |

各项存在部分重叠，且现有标定和 demo 可复用；综合去重后的合理区间为 **25～40 人日**，而不是
简单相加后的最高值。这里估算的是达到 refined 台架验收标准的工程量，不含后续实飞认证。

## 5. “1～2 天版本”会缺少什么

一两天可以合理交付的范围通常只能是：打开相机、识别单个 Tag、读取一条 Odin 位姿、运行现成
公式并打印候选结果。它通常不会同时具备：

- 正确的历史时间同步和时钟域处理；
- 多帧收敛、质量门、失败终态和严格日志；
- extnav 原链不断流、session/revision/CAS 和重启失效；
- 速度、姿态、协方差的一致变换；
- apply=false/apply=true、ACK、clear 和三路数据量化；
- 独立服务、GUI、部署脚本、自动测试和真机故障回归。

如果这些条件不在验收范围，老师的一两天判断可以成立；如果按 refined 原文验收，则这两种工作
不能视为同一个任务。

## 6. 可直接用于说明的表述

> 一两天能完成的是基于现成标定和 demo 的 AprilTag 修正量演示。Task 27 refined 实际要求把它
> 接入 400 Hz Odin 和 ArduPilot extnav 生产链，并保证时间同步、质量收敛、事务式 ACK、Odin
> 重启失效、服务崩溃不断流、地面 UI、部署备份、自动测试和真机回归。这些要求把算法小实验变成
> 了跨视觉、ROS 2、状态估计和飞控安全边界的系统工程。按熟悉该技术栈的单人估算约 25～40
> 人日，即一个多月至两个月；实飞精度验收还应另行计算。

本评估依据 refined 任务原文和任务 27 的实际交付/调试记录，不以“代码最终已经写出”倒推它本应
只需同等日历时间，也不把尚未完成的实飞精度验证包装进当前成果。
