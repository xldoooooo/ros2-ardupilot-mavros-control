## 1. 结论摘要

总体结论：**最终 `HEAD=5b15b940` 可以构建，现有自动化通过，本地 Qt→ROS 2→SITL 的初始化、起飞、手动增量/悬停、直线航点、降落和清理均可工作；但 Grok 的工作不能评价为“完全到位”。**

没有发现昨日最终提交偷偷改动 `DobController`、控制参数文件或原始 PD+DOB 算法。昨日对机载 C++ 的最终改动只涉及航点策略字段的接收与回退，不涉及控制器数学实现。

已证实的问题如下：

1. **高风险：航点服务协议已经变更，但接口仍宣称为 `1.0`。** 本机地面站与机载端同时重建时可用，但新地面站连接未升级的旧机载端时，现有版本检查会错误地认为兼容，实际 `ExecuteWaypoints` ROS 服务类型已不一致。
2. **任务未真正完成：MAVROS 启动日志降级规则没有匹配生产源名。** 规则测试使用 `mavros`，真实进程源名是 `mavros_sim`。本次真实 SITL 观察到 202 条 MAVROS ROS `[INFO]` 仍被标为 INFO。
3. **曾经实际破坏仿真功能：** Grok 自己的回归修复报告明确承认，工作过程中曾把 GUI 缓存的杭州原点写入 SITL，使 local ENU 偏移数百万米并让 RViz 机身/坐标轴不可见；同时残留 `fake_pose` 调试发布者造成位姿交替。最终代码已回退，本次实测也确认当前位姿恢复正常。
4. **修复后仍遗留错误 UI 文案：** 当前代码虽然禁止仿真写入缓存原点，但界面多处仍提示“启动本地仿真时写入原点”，与真实行为相反。
5. **航点策略产品语义不理想：** UI 允许选择“自动避障”和“遇障悬停”，机载端却接受请求后静默改为直线飞行。确认框和报告有提示，因此不属于隐瞒，但在飞行软件中仍不应让未实现策略呈现为可执行选项。
6. **测试/证据链不足：** Grok 在最终原点修复和策略改动后没有做完整在线 SITL 复飞；相关报告如实写了这一限制。本次审计补做后核心闭环通过。部分视觉证据路径已失效或不符合 `AGENTS.md` 的过程文件目录要求。

因此，未发现“最终版本已把核心飞控算法偷偷换掉”的证据，也没有证据证明 Grok 有主观造假意图；但确有一次严重功能回归、多项仍留在最终代码中的实质缺陷，以及若干验证和规范执行不到位之处。

## 3. 已证实的技术问题

### 3.1 [高] 服务定义变更但接口版本未升级

证据：

- `src/guided_interfaces/srv/ExecuteWaypoints.srv` 新增三个策略常量和 `flight_strategy` 请求字段；
- `ground_station_core/config.py:29` 仍为 `INTERFACE_VERSION = "1.0"`；
- `src/onboard_control/src/onboard_control_node.cpp:22` 仍发布 `kInterfaceVersion[] = "1.0"`；
- `src/guided_interfaces/package.xml` 与 `src/onboard_control/package.xml` 仍为 `1.0.0`；
- 连接流程只比较上述字符串版本，字符串相同就继续申请租约和调用服务。

影响：

- 本机同时重建新接口与新节点不会失败，本次构建和 SITL 也因此通过；
- 若无人机端仍部署 `703d8990/4e17c589` 一类旧接口，新地面站会把其 `ControlStatus.interface_version=1.0` 当作兼容；
- 但 `ExecuteWaypoints` 请求类型已经改变，服务发现/调用会失败或超时，无法由当前版本门控提前给出清晰的“不兼容”错误；
- 这违背了项目把 `interface_version` 作为地面站/机载部署兼容闸门的设计目的。

建议：在下一次实机部署前优先修复。至少把协议版本统一升级到 `1.1`（若遵循破坏性变更策略也可升 `2.0`），同步 Python/C++ 常量、包版本、MEMORY 和部署说明，并增加“旧地面站/新机载端、 新地面站/旧机载端”不兼容测试。

### 3.5 [中] 未实现的飞行策略被当作可执行选项接受

证据：

- GUI 下拉框提供“直线飞行 / 自动避障 / 遇到障碍悬停”；
- 地面站会把所选值写入新服务字段；
- 机载 `on_execute_waypoints()` 对所有非直线值只打 WARN，然后改为直线并返回 `accepted=true`；
- 未知数值同样不拒绝，也会回退到直线；
- 报告、tooltip 和危险确认框均提示尚未实现。

因此该项不是“偷偷把避障改成直线”：Grok 在报告和界面中有披露。但是，从飞行安全与可验证语义看，“选择 A、接受成功、执行 B”仍然不理想。

建议二选一：

1. 在能力真正实现前，只开放“直线飞行”，另外两个选项显示“未实现”并禁用；或
2. 机载端明确拒绝非直线策略，响应 `accepted=false` 和清晰原因。

无论采用哪种方案，都应拒绝未知枚举值。若今后真正实现避障，还应把机载能力/当前执行策略加入权威状态，而不是只依赖 GUI 所选值。
